# intake - контекст AI-агентов

Канонический файл проекта. Держим коротким; детали живут в `docs/`. Общие
общие конвенции проектов (язык, ветки, релизы, CHANGELOG, безопасность)
живут во внутренней базе знаний; здесь только специфика проекта.

Репозиторий: `github.com/galera-club/tg-intake`, публичный. Всё, что попадает в
коммит, читается посторонними: ни секретов, ни персональных данных, ни
внутренних имён сотрудников и клиентов.

## Проект

Сервис `intake` (репозиторий `tg-intake`, продуктовое имя «Предложка») -
Telegram-бот, который связывает тех, кто ставит задачи, с теми, кто их делает.
Бот принимает обращения по работающим сервисам, доводит их интервью до пригодного
к работе описания, заводит тикет в GitHub Issues нужного проекта, показывает его
статус по меткам, сам зовёт автора при смене статуса и новом комментарии и даёт
отменить свой тикет; проект подключается командой `/project`. Второй вход -
«Спросить»: ответ по md-файлам репозитория со ссылкой на источник и переход в
тикет по просьбе о правке. Следом - брифинг нового проекта. Границы, порядок
функций и деление - [docs/prd.md](docs/prd.md).

Цель - убрать из процесса человека, который переводит сырой фидбек в постановку.
Это рабочий инструмент, а не витрина: минимальная рабочая модель важнее
продуктового polish.

## Принципы

1. **Core против Изменяемого.** Каркас (поток, схема БД, контракты интеграций,
   инварианты) меняется дорого и защищается. Правила поведения (контракт
   готовности, тексты, карта документов, предел вопросов) живут данными и
   меняются свободно, без миграции. Разделение по функциям - раздел 4 PRD.
2. Минимум кода: ни функций, ни интерфейсов, ни файлов «на будущее». Структура
   плоская, имя файла равно ответственности.
3. Сначала модель состояния, потом код.
4. Побочные эффекты выполняет детерминированный Go. LLM возвращает недоверенный
   структурированный вывод; Go валидирует его до БД, outbox и внешних API.
5. Логирование - часть каждого среза: действие автора и решение сервиса
   наблюдаемы, новый side effect сопровождается логом.
6. Строка на русском для пользователя живёт в одном из двух файлов: `texts.go`
   (чат: сообщения, toast, кнопки, команды, уведомления владельцу, стиль §11
   спеки) или `texts_model.go` (ввод модели, тело issue, метки, словари сверки,
   ошибки и логи - байт в байт, без стиля). Новая строка вне них роняет
   `TestTextsInOneFile` (`internal/app/texts_test.go`, R9 §10 ticket-form.md).

## Стек

Модуль `github.com/galera-club/tg-intake`. Прямых зависимостей три, остальное -
стандартная библиотека; обоснование - раздел 1 [architecture](docs/architecture.md).

- Go 1.25, PostgreSQL 16 (данные и очередь через `FOR UPDATE SKIP LOCKED`)
- `gopkg.in/telebot.v4` - Bot API; `github.com/jackc/pgx/v5` - драйвер и пул;
  `github.com/pressly/goose/v3` - миграции, бинарь в образе
- `log/slog` (stdlib) - JSON-логи; OpenRouter и GitHub - свои клиенты на
  `net/http`, SDK не тянем; ffmpeg не нужен - модель принимает ogg/opus
- Модели: `OPENROUTER_MODEL_MEDIA` (голос, скриншоты) и
  `OPENROUTER_MODEL_DIALOG` (интервью, саммари, ответ по документации), бюджет
  размышлений `OPENROUTER_REASONING_DIALOG`: без предела шаг думает дольше

## Структура

`docs/` - prd, architecture, contracts, llm, state, backlog, plans/, acceptance/.
`deploy/` - safe-ssh.sh и prod/docker-compose.coolify.yml.
`src/` - cmd/intake/, migrations/, Makefile, Dockerfile, .env.example, а
`src/internal/app/` - весь рабочий код плоско, плюс prompts/ и rules/.

## Команды

Всё из `src`: `docker compose up -d postgres`, `make migrate-up`, `make run`,
`make test`, `make vet`, `make ci-check`, `make migrate-reset`. `migrate-*`
отказываются работать с не-localhost базой без `ALLOW_REMOTE=1`; тесты с базой
идут только при заданном `TEST_DATABASE_URL`, иначе молча скипаются: без
переменной прогон закрывает срез не полностью.

Новый тест оправдан, только если сломанный код его роняет: прежде чем оставить
тест, мысленно сломать покрываемую строку и назвать, что упадёт. Не падает - тест
не пишется. Один сценарий спеки - один тест.

Обязательные переменные: `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`,
`TELEGRAM_ALLOWED_IDS`, `OPENROUTER_API_KEY`, `GITHUB_TOKEN`; проекты контура -
`PROJECTS`, алерты владельцу - `ALERT_CHAT_ID` и `ALERT_BOT_TOKEN`, тема группы
алертов - `ALERT_THREAD_ID` (пусто - без темы). Полный список с дефолтами -
`src/.env.example`.

Диагностика контура - только через `deploy/safe-ssh.sh` из корня, без аргументов
печатает список действий; все read-only, произвольный ssh не используем. `cases`
и `case` печатают тексты обращений и ФИО: в терминале допустимо, в коммите нет.
Переменные контура показывает `deploy-config`, `app-env` - лишь окружение.

Проверка выката: зелёный workflow означает «Coolify принял запрос», а не «версия
выкачена» - сверять `app_revision` из `health` с кандидатом: старый контейнер
остаётся healthy и при несостоявшемся деплое.

## Workflow

Пайплайн задачи и инженерные дефолты платформы - внутренняя база знаний вне
репозитория. Технические решения - `docs/architecture.md`, нетривиальный срез
получает спеку `docs/plans/plan-*.md` до реализации и паспорт
`docs/acceptance/<slug>.md` после; у закрытого среза от спеки остаётся выжимка
«что вышло иначе и почему».

Ветки: единственная - `prod`; срез в `feature/<slug>`, PR в `prod`, после мерджа
ветка удаляется. Деплой контура только по тегу `v*` и команде владельца (workflow
`Deploy`), автодеплоя по push нет. Dev-контура нет: понадобится - заводится по
runbook базы знаний.

Метод интервью взят из промта брифовщика (внутренняя база знаний): разбор случая,
детектор выдумки, замок пересказа «где я ошибся», признак тянет вопрос. Промт бота
- свой файл, а не копия: сверяться, не тащить целиком.

## Критические инварианты

- **Медиа не переживает обращение.** Файл нужен до подтверждения саммари; после
  публикации удаляется, остаются текст и `file_id`. Ни в git, ни в логи.
- **Обезличивание до публикации.** Без персональных данных клиентов:
  идентификаторы карточек и статусы остаются, ФИО, телефоны и переписка - нет.
  Правило одно для разбора экрана, транскрипта и ответа по документации.
- **Единственный источник истины по статусу - метка issue.** Свои метки сервис
  ставит дважды: `type:`, `status:new`, `author:`, `incomplete` при публикации и
  `status:cancelled` при отмене. Дальше только читает: `cases.told_status` хранит
  не статус, а то, о чём автору уже сказали.
- **Экстрактор обязан признаваться в непрочитанном.** Схема извлечения содержит
  поле «не разобрано»: правдоподобная выдумка хуже пробела, её примут за факт.
- **Тикет не публикуется без подтверждения автора.** Саммари ловит неверно
  прочитанный скриншот, сверка показывает там же пересечения с уже сделанным.
- **Нормализация до диалога, изображение последним.** Аудио и текст первыми,
  скриншоты после них и с протоколом сырья в контексте. Медиа входит в модель
  один раз, в историю диалога - только текст.
- **Авторство не теряется.** ФИО из Telegram уходит в шапку тела issue и в метку
  `author:<slug>`: GitHub не даёт создать тикет от чужого имени. Обезличивают
  данные клиентов, не автора.
- **Доступ по белому списку Telegram ID.** Список в конфиге, чужому отказ.
- **Егресс наружу может быть закрыт.** С хоста контура прямой путь к OpenRouter
  отвечает `403`. Прокси задаётся клиенту отдельно (`OPENROUTER_PROXY`,
  `TELEGRAM_PROXY`): общий увёл бы в туннель и GitHub.
- **Порядок промта фиксирован:** стабильный префикс (инструкция плюс контекст
  проекта) впереди и кэшируется, волатильное (сырьё, дерево файлов, история)
  сзади. Изменяющаяся строка в префиксе молча гасит кэш.
- **Ни одна идея не выбрасывается.** Отклонение всегда с причиной и доступно
  автору; недобор даёт тикет с меткой `incomplete` и строкой «Не уточнено», а не отказ.
- **Мультипроектность с первого дня.** Проект - строка в таблице (`owner/repo` и
  контекст для промта), токен GitHub один на сервис. `/project` заводит проект без
  деплоя; `PROJECTS` из конфига контура синхронизируется в ту же таблицу при старте.
- **Работа с побочным эффектом идёт через таблицу `jobs`**, идемпотентна по полю
  `key` и оставляет аудит в `case_events`. Синхронно из обработчика уходят
  ответы автору, скачивание вложения и чтение GitHub для `/tickets` и
  `/project`: автор ждёт ответа сразу. Новости приносит слежение - четвёртая
  горутина раз в пять минут.
- **Нормализация не знает, чем кончится разговор.** Сырьё превращается в текст
  одинаково для любого режима: в шаге нормализации нет ни типа тикета, ни
  issue. Единственная развилка по `cases.mode` стоит в закрывающем шаге - это и
  делает второй режим бота наслаиванием, а не переписью.
- **Ответ по документации держится источником.** Только md-файлы репозитория
  проекта; ответ, источники которого не скачаны этим же ходом, не отдаётся вовсе.
  Ссылку строит Go по ветке из ответа GitHub, модель адресов не пишет. Переход из
  вопроса в тикет односторонний.
