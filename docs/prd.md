# PRD: tg-intake (Предложка)

Дата: 2026-08-08, актуализирован 2026-08-14 срезом «вопросы по документации».
Заказчик - владелец продукта, он же разработчик.
Требования собраны в диалоге с агентом, заказчик технический.

Документ описывает замысел на день разговора. Проект сырой, поэтому описание
жёстко разделено на две части:

- **Core** - каркас, который дорого менять после написания кода: границы,
  поток данных, схема хранения, контракты интеграций, инварианты безопасности.
- **Изменяемое** - правила поведения, которые будут меняться по ходу работы:
  состав вопросов, тексты, статусы, набор экранов. Они живут данными, а не кодом.

Правило разделения: если изменение требует миграции БД, нового внешнего доступа
или переписывания потока - это Core. Если достаточно правки файла промта,
конфига или одной таблицы правил - это Изменяемое.

## 1. Задача и цель

**Задача.** Фидбек по работающим сервисам приходит владельцу в личку Telegram
россыпью: голосовые, скриншоты карточек лидов, ссылки. Владелец слушает
голосовое, вычленяет суть, переформулирует агенту, и только после этого
начинается работа над спекой. Владелец работает переводчиком между сырым
фидбеком и агентом.

**Как решается сейчас.** Вручную. Правки от сотрудников по соседнему сервису
накапливаются в переписке, часть теряется, часть требует нескольких переспрашиваний, чтобы
понять, что конкретно сломалось. Отдельного места, где эти правки лежат,
нет: они попадают в `docs/backlog.md` проекта после ручного разбора.

**Кто получит результат.** Владелец: он берёт тикет и начинает с него спеку без
уточняющих вопросов автору. Автор обращения получает подтверждение с номером и
ссылкой и видит движение тикета (M4, реализовано).

**Что должно измениться.** Автор описывает проблему боту и получает номер
тикета. Владелец видит тикет, пригодный к разбору без переспрашивания. Поток
правок в личку прекращается.

**Что уже пробовали.** Ничего. Правки принимались потоком в мессенджер.

**Куда это идёт дальше.** Приём тикетов - первая функция, а не весь замысел.
Та же работа переводчиком возникает и раньше тикета: новый проект сегодня
рождается в личных разговорах и в чужих файлах произвольного вида. Конечная
цель - один канал, через который бизнес разговаривает с разработкой:
и про новый проект, и про правку в работающем сервисе.

## 2. Границы сервиса

**Назначение.** Конечное: единая точка входа бизнеса в разработку. Сотрудник
приходит в один бот и заводит новый проект, создаёт тикет по работающему
сервису и следит за его движением, не выходя в личку и не открывая GitHub.

Сегодня из этого сделано три четверти: бот принимает обращения сотрудников
команды в Telegram, доводит их до пригодного к работе описания и заводит тикет в
GitHub Issues нужного проекта, показывает движение тикета (M4), сам зовёт автора
при смене статуса и новом комментарии (M8) и отвечает на вопросы про работающий
сервис по документации его репозитория (M7). Не сделан брифинг нового
проекта (M6).

**Четыре функции и порядок.**

| Функция | Что даёт | Когда |
| --- | --- | --- |
| Создать тикет | обращение доведено до issue, пригодного к спеке | M1 плюс M2, реализовано |
| Смотреть движение тикета | статус и уведомления без личных вопросов владельцу | M4, реализовано и принято |
| Спросить про проект | ответ по документации проекта со ссылкой на источник | M7, реализовано |
| Завести новый проект | интервью с заказчиком, на выходе PRD в известном формате | M6, следующий большой этап |

Порядок не произвольный. Функции опираются друг на друга: и вопрос, и брифинг
имеют смысл, когда бот уже умеет вести структурированное интервью (M2). Вопросы
про проект вышли раньше брифинга: условие входа было «накопить PRD проектов», но
источник нашёлся готовым - документация репозиториев ведётся по общему канону, а
обязательная ссылка на файл закрыла и второе условие, проверяемость ответа.

**Соседи.**

| Кто или что | Что делает | Что остаётся ему после запуска |
| --- | --- | --- |
| Владелец | разбирает тикеты, пишет спеки, ведёт разработку | вся разработка целиком, сервис только доставляет тикет |
| GitHub Issues | хранит тикеты и их статусы | единственный источник истины по тикету и статусу |
| `docs/backlog.md` проектов | milestones и активные задачи | планирование; сервис туда не пишет |
| Заказчик бизнеса | приоритеты, решение делаем или нет | приоритизация целиком; с M6 становится ещё и пользователем бота на брифинге |
| Сотрудники | находят проблемы и предлагают правки | формулировка проблемы, но с помощью бота |

**Сервис не делает.**

- Не планирует, не приоритизирует, не назначает исполнителей и не ставит сроки:
  решение и приоритет остаются за людьми. Брифинг тоже не решает, делаем проект
  или нет: убираем перевод, а не власть.
- Не заменяет GitHub: обсуждение идёт в issue, бот показывает статус, краткое
  содержание и последний комментарий. Полного тела не показывает - на экране
  телефона оно вытесняет то, за чем зашли; отвечать разработчику из бота нельзя,
  правки идут в issue, поиска и фильтров по списку нет.
- Не отвечает по коду и по чужой памяти: источник - только md-файлы репозитория
  проекта, ответ без ссылки на файл не отдаётся вовсе. Расхождение документации
  с кодом бот не увидит и повторит документ. Документацию не правит, по
  нескольким проектам сразу не ищет и обращение ответом не отсекает.
- Не хранит медиа после обработки и не показывает ничего вне Telegram: ни
  веб-интерфейса, ни дашбордов, ни отчётов.
- Не проставляет метки статуса из CI и не выключает проект из бота: и то и
  другое делается руками, а единственным источником истины остаётся сама метка.

## 3. Юзеркейсы и развилки

### Вход и результат

**Что на входе.** Сообщения в личке Telegram-бота: текст, фотографии и
скриншоты, голосовые, ссылки на карточки CRM и на переписки. Одно обращение -
это пачка сообщений подряд. Объём: единицы обращений в день, в пике десяток.
Самый тяжёлый реальный случай на сегодня - голосовое на несколько минут плюс
три-четыре скриншота карточки.

**Что на выходе.** Issue в GitHub-репозитории проекта: заголовок, шапка с
автором, тело по контракту готовности, список нераспознанного и раздел «Ссылки»
с адресами из сырья. Метки: тип, статус, автор и `incomplete` при недоборе.
Автор получает в боте номер и ссылку.

**Что считается годным.** Тикет годен, если владелец может начать по нему спеку
без единого уточняющего вопроса автору. Негодный: «бот неправильно определяет
лида» без карточки, даты и ожидаемого поведения.

**Что делать с непригодным входом.** Файл не скачался, формат не распознан,
транскрибация пустая: бот говорит об этом прямо и просит прислать иначе.
Обращение не теряется, черновик сохраняется.

### Узнавание участника

**Признак.** Telegram ID отправителя. Доступ к боту закрыт белым списком ID в
конфиге сервиса: чужому бот отвечает отказом и обращение не заводит. Список
правится переменной окружения и рестартом, деплой не нужен.

**Авторство.** При первом обращении сервис сохраняет ФИО из профиля Telegram
(`first_name`, `last_name`, `username`) и публикует его в шапке issue плюс
меткой `author:<slug>`. Автором issue в GitHub остаётся владелец токена: API не
позволяет создать тикет от чужого имени без GitHub-аккаунта сотрудника и его
явной авторизации. Авторство фиксируется телом тикета и меткой, а не полем
GitHub.

Обезличивание касается данных клиентов, не автора: ФИО сотрудника - это
атрибуция обращения и удаляться не должно.

Чужой ID получает отказ без записи в базу; знакомый впервые заводится с ФИО;
изменённое в Telegram ФИО обновляется при следующем обращении; автору
брошенного черновика бот предлагает продолжить или начать заново.

### Правила решения

Правила добивания, состав контракта готовности и предел вопросов относятся к
блоку «Изменяемое» и вынесены в раздел 4Б. Core фиксирует одно: тикет не
публикуется, пока валидатор Go не подтвердил, что обязательные поля контракта
заполнены, либо автор явно не выбрал отправку с пометкой неполноты.

### Терминальные состояния

| Состояние | Что означает | Что видно в системах |
| --- | --- | --- |
| Тикет создан | обращение доведено до issue | issue с меткой статуса, автор получил номер и ссылку |
| Тикет создан неполным | автор не смог закрыть контракт | issue с меткой `incomplete` и строкой «Не уточнено» в теле |
| Черновик брошен | автор не завершил и не вернулся | запись в БД, issue нет, автор может продолжить позже |
| Обращение отменено | автор отказался в процессе | запись в БД, issue нет |
| Тикет отменён автором | автор отменил уже созданный тикет из карточки | issue закрыт как `not planned` с меткой `status:cancelled`, обращение в БД остаётся опубликованным |
| Разговор закрыт ответом | автор спросил по документации и получил ответ | запись в БД со статусом `answered`, issue нет |

Вопрос, заданный в режиме тикета, отдельным исходом не является: он тоже
становится тикетом, с меткой `question`. Ответ владельца идёт в issue и доходит
до автора тем же путём, что и смена статуса.

Разговор по документации - отдельный вход и отдельный исход. Бот, уверенно
отвечающий неправду про работающий сервис, хуже молчащего, поэтому ответ
держится на источнике: не нашлось файла, из которого взят факт, - автор получает
прямое «в документации этого нет». Тот же инвариант, что и «экстрактор обязан
признаваться в непрочитанном».

### Кейс 1: создание тикета

**Когда начинается.** Автор открыл бота либо просто написал ему.

**Участник.** Сотрудник команды.

**Ход.** Автор выбирает проект и накидывает сырьё пачкой: текст, голосовые,
скриншоты, ссылки, пересылки чужих сообщений; пересланное равнозначно
написанному самим автором. Свободное сообщение вне обращения не сохраняется -
управление кнопками, открытый текст только внутри обращения (решение владельца
2026-08-09). После «Готово» сырьё нормализуется в протокол (изображения
последними, с протоколом в контексте), диалоговая модель добивает недостающие
пункты контракта раундами по 2-3 вопроса с предполагаемыми ответами. Готовый
черновик сверяется с состоянием проекта: то, что уже выпущено, заведено или
запланировано, автор видит в саммари со ссылками. Автор подтверждает саммари,
бот публикует issue и отдаёт номер и ссылку, медиа удаляются. Пошаговый
интерфейс описан в README и architecture.md.

**Развилки.**

| Где | По какому признаку расходится | Куда ведёт |
| --- | --- | --- |
| сбор | вложение тяжелее 20 МБ | Bot API такой файл не отдаёт: просьба прислать иначе |
| нормализация | вложение не скачалось или не распозналось | просьба прислать иначе, обращение не теряется |
| разбор | тип обращения - вопрос | тот же путь, тикет получает метку `question` |
| интервью | автор ответил не на все вопросы раунда | переспрос только по незакрытым пунктам и не больше двух раз на пункт, дальше пункт остаётся пробелом |
| интервью | автор нажал «Отправить как есть» | раунд закрывается без ответа, дальше саммари с пометкой о незакрытых пунктах; повтор или нажатие после ответа этого раунда - без действия |
| саммари | черновик пересекается с выпущенным, заведённым или запланированным | автору показан список пересечений со ссылками; решение за ним, тикет уходит с разделом «Пересечения» |
| интервью | достигнут предел раундов | разговор идёт к саммари с пометкой о неполноте, автор решает кнопками «Публикую», «Поправить», «Сброс» (решение 2026-08-09: функционально та же развилка из трёх выходов, отдельного экрана нет) |
| саммари | автор поправил саммари | возврат к разбору с поправкой |
| публикация | GitHub недоступен | issue уходит в outbox и создаётся повторной попыткой, автор получает номер после успеха |
| любой | автор нажал «Сброс» | обращение с материалом переспрашивает подтверждение; отмена безвозвратна, возврат в начало; из публикации сброса нет |

**Чем заканчивается.** «Тикет создан» либо «Тикет создан неполным».

### Кейс 2: вопрос по документации

**Когда начинается.** Автор выбрал проект и нажал «Спросить» вместо «Создать
тикет».

**Ход.** Автор пишет или наговаривает вопрос и жмёт «Готово» - порядок тот же,
что при сборе тикета. Бот читает md-файлы репозитория проекта и отвечает по
существу, приложив ссылку на файл, откуда взят факт. Под ответом два выхода:
«Создать тикет» и «Закончить разговор». Следующий вопрос задаётся тем же
порядком.

**Развилки.**

| Где | По какому признаку расходится | Куда ведёт |
| --- | --- | --- |
| ответ | в документации ответа нет | прямое «этого в документации нет», разговор продолжается |
| ответ | автор просит правку, а не спрашивает | разговор сам переходит в создание тикета, установленный факт остаётся в истории |
| ответ | автор нажал «Создать тикет» | то же одним тапом; переход односторонний, обратно в вопрос хода нет |
| поход в документацию | GitHub или модель недоступны | бот говорит об этом, разговор возвращается в сбор, вопрос не теряется |

**Чем заканчивается.** «Разговор закрыт ответом» либо один из исходов кейса 1,
если разговор перешёл в тикет.

### Кейс 3: автор молчит

**Когда начинается.** Автор начал обращение и не отвечает.

**Шаги.** Через сутки бот один раз напоминает про незавершённый черновик. Ответа
нет - черновик остаётся доступным, повторных напоминаний нет.

**Чем заканчивается.** «Черновик брошен».

### Кейс 4: внешняя система недоступна

**Когда начинается.** Не отвечает OpenRouter, GitHub или Telegram.

**Шаги.** Внешние вызовы идут через outbox с повторами. Автор видит, что
обращение принято, и получает результат после восстановления. Упавшие работы
очереди видны владельцу в логах и диагностике; алерта об упавшей работе нет - в
его чат уходит только движение тикета.

**Чем заканчивается.** Тот же исход, что и в основном кейсе, с задержкой.

## 4. Функции

### 4А. Core: без этого сервис не работает

| Функция | Что делает | Уверенность |
| --- | --- | --- |
| Белый список | пускает к боту только известные Telegram ID | твёрдо |
| Меню проекта | список проектов, дальше список действий; обращение привязано к репозиторию до разбора, а спросить проект можно и после первого сообщения | твёрдо |
| Авторство | сохраняет ФИО из Telegram, выносит в шапку issue и в метку `author:<slug>` | твёрдо |
| Сбор пачки сырья | копит сообщения обращения до «Готово»: текст, фото, голос, ссылки | твёрдо |
| Нормализация голоса | голосовое в транскрипт, до разбора изображений | твёрдо |
| Склейка протокола сырья | собирает нормализованные куски в один текст, схлопывает дубли | твёрдо |
| Нормализация изображения | последним шагом, с протоколом сырья в контексте: скриншот в структуру по схеме, включая поле «не разобрано» | твёрдо |
| Режим разговора | «Создать тикет» или «Спросить» на входе; режим выбирает, чем кончится нормализация, и меняется только в сторону тикета | твёрдо |
| Ответ по документации | читает md-файлы репозитория проекта и отвечает со ссылкой на источник; без источника ответа нет | твёрдо |
| Интервью | добивает недостающие пункты контракта раундами по 2-3 вопроса с предполагаемыми ответами | твёрдо |
| Подтверждение | показывает саммари и правится по замечаниям автора | твёрдо |
| Публикация issue | создаёт issue в репозитории проекта через outbox | твёрдо |
| Ответ автору | отдаёт номер и ссылку | твёрдо |
| Удаление медиа | стирает файлы после подтверждения, хранит только текст и `file_id` | твёрдо |
| Черновики | сохраняет незавершённое обращение и позволяет вернуться | твёрдо |

### 4Б. Изменяемое: правила, которые будут меняться

| Функция | Что делает | Уверенность | Где живёт |
| --- | --- | --- | --- |
| Контракт готовности | набор обязательных полей по типам обращения | выбрано | файл правил в репо |
| Типы обращения | баг, доработка, вопрос | выбрано | файл правил |
| Правила добивания | порядок вопросов от ручной практики к желаемому, уточнения внутри вопроса, догадка перечисляет названное автором, 2-3 вопроса в раунде | твёрдо | промт |

**Изменяемое не означает отложенное.** Часть этих функций входит в первую
рабочую версию. Разделение говорит другое: их правка не должна требовать
пересмотра схемы данных или потока.

## 5. Как заказчик проверит результат

**Задача решена, если.** Владелец берёт тикет из GitHub и начинает спеку, ни разу
не написав автору уточняющий вопрос. Поток правок в личку прекращается.

**Проверка руками.** Сценарии приёмки живут в паспортах `docs/acceptance/`,
по одному на срез; приёмка выполнена по ним.

## 6. Внешние системы и доступы

| Система | Зачем нужна | Владелец доступа | Что передать разработчику |
| --- | --- | --- | --- |
| Telegram Bot API | приём обращений, ответы, скачивание вложений | владелец | токен нового бота |
| OpenRouter | нормализация медиа и диалог | владелец | ключ есть, отдельный лимит на сервис |
| GitHub | создание issue, чтение статусов и документации, карточка на доске организации | владелец | fine-grained PAT организации на все репозитории проектов: Issues: read and write, Contents: read для режима «Спросить», право организации Projects: read and write для доски |
| Coolify | единственный контур, он же прод | владелец | сервис, база, переменные |

Секреты в документ не пишутся, только перечень.

Токен один на сервис, а не на проект: в таблице проектов лежат `owner/repo` и
контекст, доступ общий. Отдельный токен на проект - это ключи в БД и их ротация,
цена без выгоды при одном владельце всех репозиториев.

## 7. Риски

Срок плавающий решением владельца 2026-08-08: за датой нет внешнего события, а
резать функциональность до сырого потока дороже опоздания. Ниже - только
незакрытые риски.

| Риск или допущение | Откуда знаем | Цена ошибки |
| --- | --- | --- |
| Поднятый порог отпугнёт автора, и он вернётся в личку | предположение | затея теряет смысл |
| Экстрактор теряет деталь со скриншота, а файл удалён | предположение | неверный тикет, лечится подтверждением |

**Что скорее всего попросят переделать.** Строгость интервью в обе стороны:
после первых реальных обращений станет видно, отпугивает бот или пропускает
мусор. Содержание M6 шаткое целиком: границы брифинга задаст первый живой
прогон промта брифовщика с заказчиком, до него спека не пишется. Насколько
твёрдо остальное, говорит колонка «Уверенность» в разделе 4.
